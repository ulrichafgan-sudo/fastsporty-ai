# Maketou payment integration — VIP subscriptions

This document is the audit of how **Mike Prono** uses [Maketou](https://www.maketou.com/) as the payment provider, and how a confirmed payment becomes an **active VIP subscription**.

Use it in two ways:

1. **This repo** — understand the live checkout → VIP access path.
2. **Another website** — copy the same workflow (hosted checkout + poll cart status + activate entitlement). Do not copy Mike Prono product names blindly; keep the pattern.

Official API docs (source of truth for HTTP): [https://docs-api.maketou.com/](https://docs-api.maketou.com/)  
OpenAPI spec: [https://docs-api.maketou.com/openapi.yaml](https://docs-api.maketou.com/openapi.yaml)

---

## 1. What Maketou does (and what it does not)

Maketou is a **hosted checkout** for digital products (Mobile Money / methods they offer at pay time). Our backend never talks to Orange Money / MTN directly.

| Maketou owns | Our app owns |
| --- | --- |
| Cart + hosted payment page | Plans, prices, duration in our DB |
| Collecting money | Who the user is (Supabase Auth) |
| Cart status (`waiting_payment` / `completed` / `abandoned` / `payment_failed`) | Whether VIP is active (`subscriptions`) |
| `redirectUrl` after pay | Entitlement, RLS, referral rewards |

**Important:** the public Maketou API **does not document webhooks**. Confirmation is:

1. Create cart → get `redirectUrl`
2. User pays on Maketou
3. User returns to our `redirectURL`
4. We **GET the cart** and activate VIP only if `status === "completed"`

The route `/api/payments/webhook` in this repo is **optional / future-proof**, not the primary path.

## 2. How VIP is modeled here

Paid plans live in table `plans`. Classic is free and is **not sold**.

| `plans.name` | Sold? | Unlocks |
| --- | --- | --- |
| `classic` | no (`is_active = false`) | Classic coupons only |
| `vip` | yes | VIP coupons |
| `vip_montante` | yes | VIP coupons **and** montantes |

Prices and duration are **ours** (`plans.price_xaf`, `plans.duration_days`). Admin can change them in `/admin/plans`. They must stay consistent with the Maketou product (fixed price or *prix libre* + `customerPrice`).

After a **completed** cart:

1. `transactions.status` → `success`
2. `activateOrExtendSubscription()` writes/extends `subscriptions`
3. `has_active_vip_access()` (SQL) and `resolveVipAccess()` (TS) start returning true
4. RLS allows `coupons.visibility = 'vip'`
5. If the payer was referred, the referrer may get free days

VIP is **never** unlocked from the browser alone. Server + RLS both check an active, non-expired subscription on `vip` or `vip_montante` (admins bypass).

## 3. Architecture

```
Browser                         Our Next.js API                    Maketou
───────                         ──────────────                     ───────
/abonnement
  PlanPicker
    POST /api/payments/create  → insert transactions (pending)
                               → POST /api/v1/stores/cart/checkout
                               ← cart.id + redirectUrl
    window.location = redirectUrl  →  hosted checkout
                                         user pays
/abonnement/retour/:tx  ←──── redirectURL (no query string)
  PaymentReturnVerifier
    POST /api/payments/verify  → GET /api/v1/stores/cart/{cartId}
                               if completed:
                                 processSuccessfulPayment()
                                 activateOrExtendSubscription()
/abonnement?payment=success
/vip  (gated)
```

**Source of truth for “paid”:** Maketou cart `status === "completed"`, then our `transactions` + `subscriptions` rows.

## 4. End-to-end user workflow

### 4.1 Guest

1. Opens `/abonnement`, picks VIP.
2. Redirected to `/signup?next=/abonnement?plan=<planId>&checkout=1`.
3. After signup/login, `PlanPicker` auto-calls checkout once.

### 4.2 Authenticated checkout

`POST /api/payments/create` with `{ planId }` (session cookie required).

Server:

1. Loads active plan from DB (never trust a price from the client).
2. `assertMaketouLiveReady(plan.name)` — API key, product id, HTTPS return URL.
3. Reads profile: email, name, phone, country.
4. Sanitizes name/email; normalizes phone to E.164 (or omits phone).
5. Deletes this user’s other **pending** carts (one checkout at a time).
6. Inserts `transactions` (`status: pending`, `plan_id`, `amount_xaf`).
7. Creates Maketou cart with `redirectURL = {BASE}/abonnement/retour/{transactionId}`.
8. Stores Maketou `cart.id` on `transactions.provider_reference`.
9. Returns `{ checkoutUrl }` — browser goes to Maketou.

If Maketou cart comes back already `completed` (free / zero-price products), we activate immediately and return `/abonnement?payment=success`.

### 4.3 Return + confirm

Maketou sends the user to `/abonnement/retour/:tx` (**path only** — they often reject `?query` on `redirectURL`).

`PaymentReturnVerifier` polls `POST /api/payments/verify` every 3s (max 24 times):

- `completed` → `processSuccessfulPayment` → `/abonnement?payment=success`
- `abandoned` / `payment_failed` → mark failed → `/abonnement?payment=failed`
- `waiting_payment` → keep polling

### 4.4 Access

`/vip` calls `resolveVipAccess()`. If ok, VIP coupons render. SQL `has_active_vip_access()` still blocks rows if someone tampers with the UI.

Renewal: if the user already has an active sub, expiry **stacks** from `max(now, current expires_at) + duration_days`.

## 6. Maketou HTTP API (as we call it)

Base URL: `MAKETOU_API_URL` default `https://api.maketou.net`  
Auth: `Authorization: Bearer <MAKETOU_API_KEY>` (server only, never in the browser).

### 6.1 Create cart

`POST /api/v1/stores/cart/checkout`

```json
{
  "productDocumentId": "uuid-of-maketou-product",
  "email": "client@example.com",
  "firstName": "Jean",
  "lastName": "Dupont",
  "phone": "+2376XXXXXXXX",
  "redirectURL": "https://your-domain.com/abonnement/retour/<transaction-uuid>",
  "meta": {
    "userId": "<our-user-uuid>",
    "source": "mike_prono"
  },
  "customerPrice": 5000
}
```

| Field | Required | Notes |
| --- | --- | --- |
| `productDocumentId` | yes | Public product id from Maketou dashboard. See [product document id](https://docs-api.maketou.com/resources/product-document-id.md). |
| `email` | yes | Valid email. We trim + lowercase. |
| `firstName` / `lastName` | yes | Letters only after sanitization. Digits / accents / hyphens caused **HTTP 422**. |
| `phone` | no | E.164 (`+` and 8–15 digits). **Omit** if invalid — a bad phone 422s the whole cart. |
| `redirectURL` | no | HTTPS, **no query string**. Maketou rejects `http://localhost`. |
| `meta` | no | String map. We send camelCase `userId` + `source` like the docs. |
| `customerPrice` | no | Only if the Maketou product is **prix libre**. Must be ≥ product minimum. We send it when `MAKETOU_PRODUCT_DOCUMENT_ID` is set. |

Success **201**:

```json
{
  "cart": { "id": "...", "status": "waiting_payment" },
  "redirectUrl": "https://checkout.moneroo.io/..."
}
```

We store `cart.id` as `transactions.provider_reference` and send the user to `redirectUrl`.

### 6.2 Retrieve cart

`GET /api/v1/stores/cart/{cartId}`

Statuses we map:

| Maketou | Our transaction |
| --- | --- |
| `completed` | `success` → activate VIP |
| `waiting_payment` | stay `pending` |
| `abandoned` | `failed` |
| `payment_failed` | `failed` |

**Never** grant VIP on `waiting_payment`.

### 6.3 Error codes we handle

| HTTP | Code | Meaning |
| --- | --- | --- |
| 400 | `INVALID_PRODUCT` | Product missing, unpublished, or not this store |
| 401 | `INVALID_API_KEY` | Bad / missing key |
| 422 | `VALIDATION_ERROR` | Payload (name, email, phone, URL, …) |
| 422 | `CUSTOMER_PRICE_BELOW_MINIMUM` | `customerPrice` too low |
| 429 | `RATE_LIMITED` | Back off (`Retry-After`) |

422 bodies are sometimes NestJS `message: [{ target, property, constraints }]`. We **do not** show that JSON to users (PII). See `formatMaketouCheckoutError()`.

## 7. Environment variables

Copy from `.env.example`. Production (Vercel) must use **`MAKETOU_MODE=live`**.

| Variable | Purpose |
| --- | --- |
| `MAKETOU_MODE` | `mock` (local) or `live` |
| `MAKETOU_API_URL` | Default `https://api.maketou.net` |
| `MAKETOU_API_KEY` | Store API key (server secret) |
| `MAKETOU_PRODUCT_DOCUMENT_ID` | **Option A** — one *prix libre* product for all paid plans; we send `customerPrice` = plan price |
| `MAKETOU_PRODUCT_VIP` | **Option B** — product for plan `vip` |
| `MAKETOU_PRODUCT_VIP_MONTANTE` | **Option B** — product for plan `vip_montante` |
| `MAKETOU_REDIRECT_BASE_URL` | `https://your-domain` no trailing slash |
| `NEXT_PUBLIC_APP_URL` | Same origin as the site |
| `MAKETOU_WEBHOOK_SECRET` | Only if you later wire `/api/payments/webhook` |
| `CRON_SECRET` | Protects `/api/cron/cleanup-pending` |

Product id resolution (`getProductDocumentIdForPlan`):

1. `MAKETOU_PRODUCT_DOCUMENT_ID` if set (all plans)
2. else `MAKETOU_PRODUCT_{PLAN_NAME}` e.g. `MAKETOU_PRODUCT_VIP`
3. else fall back to `MAKETOU_PRODUCT_VIP`
4. else throw — do not call Maketou

## 8. Database (minimum to copy)

```
plans
  id, name, price_xaf, duration_days, is_active

transactions
  id, user_id, plan_id, subscription_id (nullable)
  amount_xaf, provider = 'maketou'
  provider_reference  -- Maketou cart.id
  status: pending | success | failed

subscriptions
  id, user_id, plan_id
  status: active | ...
  started_at, expires_at
```

Rules we rely on:

- Client never writes `transactions.status = success` (service-role / admin client only).
- `processSuccessfulPayment` is **idempotent**: if already `success`, return `{ alreadyProcessed: true }`.
- Before a new checkout, delete that user’s other `pending` rows.
- Cron: pending older than 24h and failed older than 7d are deleted.

Access SQL (keep TypeScript `VIP_PLAN_NAMES` in sync):

```sql
-- true if current user has non-expired vip or vip_montante
select exists (
  select 1
  from subscriptions s
  join plans pl on pl.id = s.plan_id
  where s.user_id = auth.uid()
    and s.status = 'active'
    and s.expires_at > now()
    and pl.name in ('vip', 'vip_montante')
);
```

## 9. Local mock mode

`MAKETOU_MODE=mock` (default if unset):

- `initiateMaketouPayment` does **not** call Maketou.
- Browser goes to `/abonnement/mock-pay?tx=...`.
- Buttons POST `/api/payments/mock-confirm` → same `processSuccessfulPayment` / `processFailedPayment`.
- That route returns **403** when mode is `live`.

Use mock on localhost. Live Maketou **rejects** `http://localhost` as `redirectURL`. For a real cart from a laptop, use HTTPS (ngrok / deployed preview) and set `MAKETOU_REDIRECT_BASE_URL` to that HTTPS origin.

## 10. Side effects after a successful payment

All in `processSuccessfulPayment` (server, admin client):

1. Load transaction by `transactionId` or `provider_reference`.
2. Skip if already `success`.
3. `activateOrExtendSubscription(userId, plan)`.
4. Set transaction `success` + `subscription_id` + cart id.
5. `grantPendingReferralRewards(paidUserId)` — referrer gets `reward_value` extra days if a pending referral exists.

Admin can also grant VIP without Maketou (`grantUserPlanAction`) — same `activateOrExtendSubscription`, no transaction.

## 11. Copy this onto another project

Minimal checklist:

1. **Maketou dashboard**
   - Create the store, get an API key.
   - Create one product per paid SKU **or** one *prix libre* product.
   - Publish the product. Copy `productDocumentId`.
2. **Your app**
   - Server-only env: API key, product id(s), HTTPS `redirectURL` base.
   - Authenticated `POST /payments/create`: insert pending tx → create cart → return `redirectUrl`.
   - Return path **without query params**, e.g. `/pay/return/:transactionId`.
   - `GET` cart on return; activate entitlement **only** if `completed`.
   - Idempotent activation (double poll / double return must not double-charge days unless you intend stacking — we stack on **new successful payments**, not on verify retries).
3. **Payload hygiene** (or you will get 422 in production)
   - `firstName` / `lastName`: ASCII letters, ≥ 2 chars.
   - `email`: trimmed, valid.
   - `phone`: E.164 or **omit**.
   - `redirectURL`: `https://...` no `?foo=`.
   - Keep the API key off the client.
4. **Entitlement**
   - Your own `subscriptions` (or license) table.
   - Server gate + DB policy. Do not hide premium UI only in CSS.
5. **Do not depend on webhooks** unless Maketou documents them for your account. Poll the cart.

Reuse from this repo as a library-shaped core (no UI):

- `src/lib/maketou/*`
- `src/lib/subscriptions/process-payment.ts`
- `src/lib/subscriptions/activate.ts`
- `src/lib/phone.ts`

Replace Mike-specific bits: plan names, `source: "mike_prono"`, return path `/abonnement/retour/...`, fallback last name `MikeProno`.

## 12. Pitfalls we hit in production

| Symptom | Cause | What we do |
| --- | --- | --- |
| HTTP 422, JSON dump on `/abonnement` | Invalid name (`bakary038` from email), bad phone, or URL with `?query` | Sanitize names; omit bad phones; path-only return URL; never echo 422 body to the UI |
| Checkout never starts in prod | `MAKETOU_MODE=mock` on Vercel, or missing API key / product id | `assertMaketouLiveReady` fails with 503 |
| Maketou refuses return URL | `http://localhost` or query string | HTTPS base; `/abonnement/retour/:tx` |
| User paid, still Classic | Return poll not finished, or cart not `completed` | `/abonnement/retour/:tx` polls verify; user can refresh; support checks `transactions.provider_reference` |
| Wrong amount charged | *Prix libre* product without `customerPrice`, or fixed product price ≠ `plans.price_xaf` | Option A sends `customerPrice`; Option B: match dashboard price to plan |
| Duplicate pending carts | Repeat “Choisir ce plan” | `clearUserPendingTransactions` before insert |
| 429 | Too many cart creates | Respect rate limits; don’t spam checkout on mount |

## 13. Security notes

- `MAKETOU_API_KEY` is server-only.
- Verify uses the **logged-in user** + `transaction.user_id` match — you cannot confirm someone else’s cart.
- Activation uses the **Supabase service role** because RLS forbids clients from inserting paid subscriptions.
- Webhook (if you enable it) must check `X-Maketou-Signature` against `MAKETOU_WEBHOOK_SECRET`. Treat it as untrusted until the cart GET also says `completed`.
- Do not log full checkout payloads (email, phone). We log status + truncated error body on failure.

## 14. Quick test plan

**Mock**

1. `MAKETOU_MODE=mock`, sign in, `/abonnement` → VIP.
2. Mock page → success → `/vip` shows coupons.
3. Mock fail → transaction `failed`, still Classic.

**Live** (HTTPS site)
